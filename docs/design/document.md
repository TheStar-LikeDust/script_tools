# 服务文档结构设计 (Service Doc Structure)

本文件规定 `docs/` 下每个服务说明文档的章节结构，以 `docs/deploy_services/paradedb.md` 为 Compose 服务基准模板。文档分别放入 `docs/deploy_services/`、`docs/deploy_apps/`、`docs/tools/`，与脚本目录对应。宿主机工具只描述其实际命令，不套用 Compose 生命周期。

文档约定：

- 标题必带序号：二级标题必须带数字序号（例如 `## 1. 简介`）。
- 精简通用信息：Compose 生命周期、目录即服务和共享依赖边界应在设计文档中统一说明，服务文档只保留该服务特有的配置与行为。
- 排版规范：正文避免使用加粗（`**`）与 emoji；列表用 `- 标题：说明` 的形式；代码/变量/路径用反引号包裹。
- 行文语气：面向最终用户说明，但避免使用“你”、“您的”等第二人称代词，采用客观专业的通用文档陈述语气（例如将“你需要修改”改为“需修改”）。

## 章节骨架

按以下顺序组织章节：

1. `# <服务名> 部署 (Deploy)`
2. `## 1. 简介`
3. `## 2. 核心配置项`
4. `## 3. 备注`
5. `## 4. 快速执行`
6. `## 5. 命令解释`
7. `## 6. 其他可选补充章节`

## 各章节要点

### 1. 简介

这个服务是什么、提供什么功能、在架构中起什么作用，必须精简为一两句话并放在 `>` 引用块中。随后精简地总结该服务特有的部署逻辑和硬性要求（如自动生成密码、健康探测等），合并为一段紧凑的陈述。
不单列“功能”章节，不使用“需求/痛点 -> 方案”结构；通用行为引用设计文档。

### 2. 核心配置项

每个配置文件使用三级标题单列，直接列出参数用途、默认值和必填条件。区分宿主机端口与容器端口、原始凭证与完整 URI；说明哪些变量已透传，哪些需要扩展 Compose 模板。

### 3. 备注

放该服务特有的注意点（如配置文件渲染覆写机制、特殊的目录挂载、首登行为等），通用行为不要重复写。

### 4. 快速执行

Compose 服务先给出 `init`、人工填写配置、`start` 的分步流程，随后列出 `update`。`up` 用于配置已就绪的实例。清理命令须标明删除范围；命令示例的注释使用英文。宿主机工具按自己的初始化和启动方式说明。

### 5. 命令解释

每条实际支持的命令使用独立四级小节，说明行为、保留资产与删除范围；必要时给出 CLI 命令或内部调用示意。Compose 服务须覆盖 `init/start/up/update/stop/rm/purge/reset`。若示例使用内部 `compose` 包装函数，应说明参数来源，不得暗示可以独立复制执行。初始化可有密钥生成的临时容器，但不启动常驻服务。`status` 不是标准命令。

### 6. 其他补充

说明镜像版本、服务专属备份恢复、复制目录的范围和外部反代要求。应用密钥与数据库备份的对应关系必须明确，不能将复制应用目录描述为复制全部外部数据。

### 服务特有 vs 通用

通用规则集中在 `command.md` 与 `core.md`，服务文档按需引用。应用文档须说明外部依赖地址、凭证、共享网络、远程连接和容器内 localhost 的含义，并明确生命周期不影响共享服务。功能尚未接入时写明当前边界；不保留废弃接口、空占位章节或已取消的工作清单。
