# 服务文档结构设计 (Service Doc Structure)

本文件规定 `docs/` 下每个服务说明文档的章节结构，以 `docs/openwebui.md` 为基准模板。新增服务文档时照此骨架填写，保证所有服务文档风格统一。

文档约定：
- 标题必带序号：二级标题必须带数字序号（例如 `## 1. 简介`）。
- 精简通用信息：通用的框架级废话（如“使用原生 docker run 管理”）应移出正文。
- 排版规范：正文避免使用加粗（`**`）与 emoji；列表用 `- 标题：说明` 的形式；代码/变量/路径用反引号包裹。
- 行文语气：面向最终用户说明，但避免使用“你”、“您的”等第二人称代词，采用客观专业的通用文档陈述语气（例如将“你需要修改”改为“需修改”）。

## 章节骨架

按以下顺序组织章节：

1. `# <服务名> 部署 (Deploy)`
2. `## 1. 简介`
3. `## 2. 部署特性`
4. `## 3. 核心配置项 (settings.conf)`
5. `## 4. 备注`
6. `## 5. 快速执行`
7. `## 6. 命令解释`
8. `## 7. 其他可选补充章节`

## 各章节要点

### 1. 简介
这个服务是什么、提供什么功能、在架构中起什么作用，必须精简为一两句话并放在 `>` 引用块中。随后仅补充该服务的硬性要求（如是否强依赖某数据库），不要写全局通用的编排描述。

### 2. 部署特性
列出该服务特有的部署逻辑，例如多种部署模式（如是否附带外部库）、独特的委托关系、运行期网络连通等。

### 3. 核心配置项 (settings.conf)
列出 `init` 生成的主要变量（及附带服务的配置），逐项说明用途与默认值。

### 4. 备注
放该服务特有的注意点（如配置文件渲染覆写机制、特殊的目录挂载、首登行为等），通用行为不要重复写。

### 5. 快速执行
给出最短上手命令（`up` 一键，或分步）。

### 6. 命令解释
每条生命周期命令（`init` / `start` / `up` / `stop` / `rm` / `purge` / `status`）单独一个 `####` 小节，正文用一句话说明它做了什么，再用代码块贴出该命令实际执行的核心脚本代码（如完整的 `docker run` 参数）。目的是让读者不看脚本也能判断底层行为是否合理。

### 7. 其他补充
收尾信息，如依赖 repo 结构、镜像版本说明、外部反代建议等。

### 服务特有 vs 通用

服务文档只写该服务特有的信息。通用的设计理念（命令规范、目录即服务、编排与配置注入方式、实例命名、委托式级联与 `--conf`/`--name` 通用参数、app 级网络组装等）统一放在 `docs/project/` 下的 `command.md` 与 `service.md`，服务文档不重复，必要时引用。
